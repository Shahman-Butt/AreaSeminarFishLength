Step 2 in code: building the mask

def mask_from_polygons(segmentation, size):
    mask = Image.new("L", size, 0)              # start fully black
    for polygon in json.loads(segmentation):
        points = list(zip(polygon[0::2], polygon[1::2]))
        draw.polygon(points, fill=255)           # 255 = "this pixel is the fish"
    return mask

Every fish's exact outline was already recorded by hand as a polygon (a list of x,y points) when the dataset was built. This function just "colours inside the lines".

Step 3 in code: blacken everything except this one fish

masked = Image.new("RGB", img.size, (0, 0, 0))   # solid black canvas
masked.paste(img, mask=mask)                       # copy pixels ONLY where mask==255

This is why overlapping fish disappear. Even if three fish are piled on top of each other in the original photo, only the ONE fish whose polygon is white survives into the crop — every other fish, and the table, and the background, all vanish to solid black.

Step 3b in code: a SQUARE window, not a stretched one

side = max(width, height)          # longer side wins
cx, cy = centre_of_fish
window = square of size `side`, centred on (cx, cy)

If we used a non-square rectangle and then force-resized it to 224×224 later, a long thin fish would get squashed fatter than it really is — directly corrupting the length signal we're trying to measure. Using the longer side for both dimensions avoids this entirely.

Where the bounding box comes from, and why it's needed

bbox = [ bbox_x/width, bbox_y/height, bbox_w/width, bbox_h/height ]
# these are coordinates in the ORIGINAL, un-cropped photo — NOT the crop

Every crop gets resized to the exact same 224×224 square, so a tiny sardine and a huge cod would look the SAME SIZE inside the crop alone. These 4 numbers (computed from the original photo, before cropping) are how the model recovers the fish's true scale.

How configs control every part of this diagram

One JSON file per experiment decides every knob in the diagram above. Example (configs/efficientnet_b0.json):

{
  "model": "efficientnet",          // which ENCODER box to build
  "bbox_input": true,                // whether the "+bbox hint" arrow exists at all
  "pretrained": true,                // encoder starts from ImageNet weights, not random
  "freeze_encoder": false,           // encoder box is trainable (not locked)
  "head": [512, 128, 1],             // HEAD box shape: 2 hidden layers, 1 final output
  "learning_rate": 0.0001,
  "batch_size": 16,
  "epochs": 100,
  "seed": 42
}

build_model(config) (in models.py) reads the "model" field and constructs the matching encoder class; every other field configures HOW that encoder trains (learning rate, epochs, frozen or not, head shape). Changing ONE model to a different encoder is as simple as changing that one string and re-running — nothing else in the pipeline needs to change.

Step 3 — five different "eyes"

Model gallery: how each encoder reads the image differently

Two structurally different families were tested: CNNs (scan with small sliding filters) and Transformers (chop into patches, let every patch "see" every other patch).

→

many times...
→

Each block only "sees" a small local neighbourhood of pixels; stacking many blocks slowly builds up a bigger picture, while shrinking resolution and growing feature depth.

The image is chopped into a grid of patches (violet squares) plus one special summary [CLS] token (the circle on top). Every patch can directly "attend to" every other patch in one layer — unlike a CNN, which only sees neighbours until many layers deep.

The surprising result: throwing MORE training at EfficientNet-B0 (higher learning rate, a decay schedule, double the epochs) made it worse, not better — 0.934 cm vs. the basic recipe's 0.781 cm. This is a real, useful finding: it suggests EfficientNet-B0 was already close to its ceiling on this small dataset (~11,000 training crops), and a more aggressive recipe overshoots into overfitting or instability rather than finding a better optimum.

What we deliberately did NOT try, and why

  • Multiple seeds of the 0.781 basic recipe — we prioritized testing whether a different recipe could beat the baseline over first confirming whether the 0.781 result itself was reliable. This is a gap, not an oversight we're hiding.
  • SGD or other optimizers — Adam was kept fixed across every single encoder in the whole project, specifically so the encoder comparison stayed controlled and fair.
  • Mixup/CutMix, label smoothing, warmup schedules — each adds another variable; with only single-seed runs already, adding more knobs would make it harder, not easier, to know what caused any change.
  • EfficientNet-B1/B2 (larger variants) — only B0 was in scope for this round; larger variants are listed as future work.
The question everyone will ask

EfficientNet-B0: how close, how reliable?

0.771 cmMobileNetV2
(baseline)
vs
0.781 cmEfficientNet-B0
(basic recipe)

Gap: 0.010 cm — about a tenth of a millimetre, on fish averaging ~30 cm.

Is 0.010 cm meaningful, or noise? We genuinely don't know yet. Both numbers come from a single training run each (seed 42 only). Neural network training has run-to-run randomness — the same recipe run again with a different seed could easily land 0.01–0.03 cm higher or lower purely by chance. A gap this small needs multi-seed repeats (like the DINOv2 patch-vs-CLS study got, with seeds 42/1/2) before anyone can honestly say EfficientNet-B0 "matches" or "loses to" the baseline. Right now it is accurately described only as "the closest single-model result found so far, unconfirmed."

Why might it be close at all?

💡 Hypothesis, not proven: EfficientNet-B0 and MobileNetV2 are architectural cousins — both are compact, fully-supervised, ImageNet-pretrained CNNs designed for efficiency. Both were fully fine-tuned end-to-end on this exact task. It's plausible that this whole family of small supervised CNNs is simply well matched to a masked, cropped, single-object regression task like this one — but that's an interpretation, not a demonstrated fact.

Why did the "stronger recipe" make it worse?

💡 Also a hypothesis: with only ~11,000 training crops, a 10× larger learning rate (1e-3 instead of 1e-4) combined with double the epochs may push the model past its best point and into overfitting — memorizing quirks of the training crops rather than learning generalizable size cues. The gentler "strong B" recipe (5e-4) may tell us more once it finishes.
